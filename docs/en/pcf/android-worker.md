# Optional Android worker candidate (PCF-719)

This is local development, not activation or full-flow acceptance. The Android application remains a control client. No worker UI, remote activation endpoint, credential provisioning, pairing, or phone deployment is connected. The physical phone remains control-only.

`PcfWorkerService` is non-exported and inert until its app-local binder receives explicit owner approval and a separately provisioned limited worker binding. A grant references the **existing** City/device identity, a separate worker installation and principal, and an opaque credential handle. It rejects the control installation as the worker installation. These references are not authentication: the future integration must authenticate and authorize the grant against the canonical device/installation registry before calling `activate`; this candidate does not mint or verify server credentials. It has no task store or independent physical-device identity generator.

Activation requires a visible app and an additional background-budget approval to continue after the app is backgrounded. The service uses an ongoing foreground notification with Stop, a two-minute in-memory lease, `shortService`, and `START_NOT_STICKY`. Task removal, explicit stop/revoke, OS destruction, timeout and process death remove execution eligibility; there is no reboot receiver or automatic restart. A foreground-service permission is the only new manifest permission. The existing camera permission belongs to the original scanning control client; worker code does not access cameras, microphones, location or Bluetooth. No notification-permission prompt is introduced; platform notification visibility still requires physical verification.

Visibility is observed through application `ActivityLifecycleCallbacks`, not a binder caller flag. Only resumed activities count; pause, stop and destroy remove them. Unknown initial visibility fails closed: an integration must bind before an activity resumes, or wait for the next observed resume before activation. Visibility is read afresh at dispatch and completion, so a pause refuses work/results unless the separate background budget is approved. Native lifecycle unit tests observed an actual assertion RED for the former cached-visibility behavior before the observer repair; `.runtime/pcf-stageb-android-lifecycle-red.log` and `pcf-stageb-android-lifecycle-green.log` retain this evidence. `tests/pcf719-android-edge-contract.test.mjs` adds Node source/seam guards only; it does not substitute for native or physical runtime evidence.

The only local executor is `text.normalize.v1`, synchronous whitespace normalization with a 16,384 UTF-16-code-unit input limit. It runs no shell, downloaded code or models. Before dispatch and result release the service checks its current lease and worker generation plus live OS conditions: battery at least 20%, thermal state none/light, power saving off, validated connectivity, unmetered network, and foreground/background approval. Unknown battery/thermal readings fail closed; Android 26–28 cannot supply the thermal reading used here and are consequently unavailable. Binder revoke/stop clears the grant; server-side revocation propagation and persistent authoritative grant validation remain prerequisites for remote scheduling. No results are uploaded or synthesized while offline.

Local validation uses the existing JDK 17 and SDK, with no installs: `gradlew.bat :app:testDebugUnitTest :app:assembleDebug --offline`. Evidence: `.runtime/pcf-stageb-android-red.log`, `.runtime/pcf-stageb-android-service-red.log`, `.runtime/pcf-stageb-android-green.log`, `.runtime/pcf-stageb-android-build.log`. RED runs show absent candidate types before implementation; native unit tests cover opt-in refusal, distinct installation, allowlist/input budget, each resource refusal, background approval, completion-generation fencing, stop/revoke/reclaim, and lease expiry. APK compilation and unit tests do not validate Android service runtime behavior.

Still `NOT_RUN`: service instrumentation, physical foreground notification/Stop visibility, background execution and OS reclaim, real battery/thermal refusal, network switching, permission/server revocation propagation, credential enrollment/registry role recording, approved-PC computation, original-phone result return, and cross-host review. These need owner activation for a specific Android execution service and budget, secure integration with the canonical limited-worker grant, and the one consolidated Mech handoff. Do not install this candidate on the control-only phone or count its two principals as two physical hosts. No 24/7 background availability is promised.
